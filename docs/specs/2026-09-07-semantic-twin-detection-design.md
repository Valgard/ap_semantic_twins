# Semantic Twin Detection — Design

**Date:** 2026-09-07
**Status:** Approved, ready for implementation planning

## 1. Problem

Clone detection tools (jscpd, PMD CPD, SonarQube, Simian) work on normalised token
streams or AST hashes. That covers clone types 1 to 3:

- **Type 1** — identical apart from whitespace and comments
- **Type 2** — identical structure, renamed identifiers, types, literals
- **Type 3** — near-miss: statements added, removed or altered

They are structurally blind to **type 4**: two units that are functionally equivalent
but syntactically unrelated. No hash matches, because nothing about the surface form
agrees. Type-4 clones are the ones that hurt most:

- a helper reimplemented because its author did not know the existing one
- the same rule encoded twice in different layers, drifting apart over time

The only reason to spend model tokens on this problem rather than run jscpd is type 4.
Every decision below serves that.

## 2. Scope

**In scope.** Named callable units (functions, methods) and types or classes, within one
project, across files and modules, across whichever languages the target repo contains.

**Out of scope.**

- Block-level clones. Types 1 to 3 are a tooling problem; jscpd solves them better and
  for free.
- Cross-repository comparison.
- Automatic refactoring. Merging two twins is an architecture and product decision, and
  across a bounded-context boundary duplication is frequently the correct answer. The
  tool reports and proposes; a person decides.

## 3. Architecture

Comparing N units means N² pairs — 2,000 units is 2 million pairs. So the pipeline
splits in two: candidate generation must be cheap and high-recall, verification
expensive and high-precision. Verification can only discard, never recover. Whatever
candidate generation misses is lost silently.

### Stage 1 — Inventory (deterministic, script)

`scripts/inventory.py`, standard library only. The skill invokes it as
`python3 "<skill base directory>/scripts/inventory.py"`: the audited project is the working
directory, so a relative path would resolve against it and `uv run` would bind to whatever
project sits there. Development and test runs inside this repo use `uv run` as usual.

Source is `git ls-files`, which lists **tracked** files only — `.gitignore` plays no part
in that list. A committed `vendor/` tree is tracked like anything else and is kept out
solely by the path-convention rule below, not by being ignored. Untracked files are
collected separately, with `git ls-files --others --exclude-standard` (which does honour
`.gitignore`), and are not silently absorbed: a branch-in-progress's untracked files are
common, not an edge case, so they are counted and named in their own `untracked` bucket.
That bucket is deliberately unfiltered by extension or path rule — it counts `.md` files,
images and anything under `vendor/` too — because the point is to surface everything git
does not yet consider part of the repository, not to pre-judge which of it would have
mattered.

Filters:

- language selection by a fixed extension whitelist in the source; there is no override,
  and nothing is inferred from which extensions the target repo actually contains
- generated code excluded by header heuristic (`<auto-generated`, `Code generated by`,
  `@generated`, `DO NOT EDIT`)
- excluded by path convention: a `vendor`, `node_modules`, `migrations`, `__snapshots__`,
  `dist` or `build` path segment, or a `*.min.js` or `*.generated.cs` filename suffix.
  Lockfiles are not part of this rule — they are excluded because their extensions are not
  in the language whitelist above, the same as any other unsupported extension
- files that cannot be read or decoded are counted in their own bucket, never folded into the
  path-convention count. A binary or mis-encoded source file is excluded for a reason that has
  nothing to do with its name, and a count that conflates the two hides it
- tests excluded by default. `--include-tests` runs them as a separate corpus, because
  test twins are judged by a different standard — shared fixtures and parallel builders
  are not debt

Output is JSON: the file list with per-file line counts and chunking plans, plus three
accounting structures that make what got dropped visible instead of buried:

- `excluded` — a counter per exclusion reason: `generated`, `path_rule`,
  `unsupported_extension`, `untracked`, `missing`, `undecodable`, `permission_denied`
- `excluded_paths` — the subset of those reasons that name individual files rather than
  only counting them (`generated`, `untracked`, `missing`, `undecodable`,
  `permission_denied`; `path_rule` and `unsupported_extension` are counted only), so a
  caller can act on which files were dropped, not only how many
- `unsupported_extensions` — a histogram of the extensions actually seen but outside the
  whitelist, keyed by extension with `""` for a file with none, so a language the tool
  should plausibly support but doesn't becomes visible instead of vanishing into one count

Files over 800 lines are split into overlapping blocks so no unit is cut in half.

A script rather than an agent because the step is mechanical and must be reproducible
between runs. A model call here would buy nothing and make the run non-deterministic.

### Stage 2 — Purpose extraction (fan-out, one call per file or chunk)

Each file or chunk goes to a `haiku` subagent which returns one JSONL record per named
unit:

```json
{"file": "src/Pricing/NetCalculator.cs", "line": 42, "name": "ToNetMinorUnits",
 "kind": "method",
 "purpose": "converts a gross price with a tax rate into net minor units, rounding half-up",
 "inputs": "decimal gross, decimal taxRate", "outputs": "long",
 "effects": "none", "invariants": "throws on a negative tax rate"}
```

Enumeration and comprehension collapse into a single step, which removes the parser
dependency altogether. universal-ctags is not installed on the target machine
(`/usr/bin/ctags` is the BSD build from the Xcode toolchain and supports none of C#, PHP
or JS), tree-sitter is not installed, and a per-language regex enumerator would be
fragile in exactly the languages that matter here. The call count also drops from one per
unit to one per file or chunk.

**The purpose sentence states effect, never construction.** "rounds to minor units" is
usable; "loops over line items" is not. A construction sentence describes how two twins
differ instead of how they agree, and sinks the pair. This is a hard rule in the
extraction prompt, carrying worked positive and negative examples.

The orchestrator reconciles this stage before moving on: chunks dispatched must equal
chunks that returned at least one unit plus chunks that returned nothing, the latter
counted **after** a single re-dispatch of anything that came back empty on the first try.
A chunk still empty after that re-dispatch is named by `path:range` in the report rather
than silently dropped — a lost chunk and a chunk that genuinely defines nothing are
different outcomes, and only one of them is fine.

### Stage 3 — Clustering (exactly one call, large context)

The whole index is read at once. Five thousand units at roughly 45 tokens each is about
225k tokens, comfortably inside one context window. The call groups units by purpose
equivalence and emits candidate groups, each with a stated reason and its member
locations.

This is where the design drops an entire subsystem. The textbook answer to "find similar
items among N" is embeddings plus a vector index plus nearest-neighbour search: a
provider dependency, an API key, a persistence problem, and a similarity threshold to
calibrate. When the index fits in one context window, similarity search is just reading.
The approach holds to roughly 20,000 units; beyond that, partition the index by directory
tree and merge clusters across partitions in a second pass.

### Stage 4 — Adversarial verification (fan-out, one subagent per cluster)

Each cluster goes to a subagent that reads **the actual source**, not the summaries. Its
brief is refutation: find the reason these are not the same thing.

Stages 2 and 3 operate on summaries, and summaries agree easily where source does not —
"validates user input" describes dozens of unrelated functions. Without a stage working
against its own candidate, the report is systematically optimistic. Surviving clusters
carry a divergence delta: what differs in behaviour, and which side looks like the
corrected one.

### Stage 5 — Report (orchestrator)

Reconciles verification the same way stage 2's chunks were reconciled: the four verdict
counts (`DIVERGENT` + `STABLE` + `JUSTIFIED` + `NOT_A_TWIN`) must sum to the number of
groups dispatched to stage 4. Any shortfall is a verification dispatch that came back
empty, reported as its own line rather than folded into whichever total is convenient — a
failed stage 4 call must not be indistinguishable from a group that never existed.

Divergence outranks size. Every finding cites a concrete `path:line` for each member — two
for a pair, one per member for a larger group.

### Model allocation and fan-out limits

| Stage | Model | Reason |
| --- | --- | --- |
| 2 — purpose extraction | `haiku` | Structured extraction against a fixed schema, run once per file or chunk. The volume stage; it must be the cheapest one. |
| 3 — clustering | orchestrator's own | Needs the large context window and holds the whole index at once. Not a subagent. |
| 4 — verification | inherit | Judgement work against real source. Under-powering the only stage that can refute would defeat its purpose. |

Stage 3 ranks clusters by confidence, and the orchestrator verifies them in batches with a
cap (default 40 clusters per run, or a higher cap the caller named). Without a cap, one noisy
clustering pass fans out into hundreds of verification agents.

## 4. Finding taxonomy

Four verification outcomes, plus one pre-verification exclusion that never reaches
verification at all:

| Outcome | Meaning | Treatment |
| --- | --- | --- |
| `DIVERGENT` | Same purpose, different behaviour — a **defect** | First section, with the behavioural delta and which side appears corrected |
| `STABLE` | Same purpose, same behaviour — **debt** | Second section, ranked by consolidation size |
| `JUSTIFIED` | Deliberately separate: bounded contexts, layer isolation, anti-corruption layer | Named, not counted as a finding |
| `NOT_A_TWIN` | Refuted in stage 4 | Appears only in the tally |

**`GENERATED`** — generated code, a migration, a snapshot, or a minified bundle. Excluded
before verification, counted only. It is not a fifth outcome alongside the four above: it
never reaches stage 4 to be judged against them.

`JUSTIFIED` is not politeness, it is the condition for the tool being used at all.
Without a legitimate "this is fine" outcome, the report becomes a wall of noise and is
ignored after two runs.

`DIVERGENT` outranks `STABLE` because a drifted twin is a latent bug — a fix, an edge
case or a validation landed on one side only — whereas a stable twin is maintenance load
and nothing worse.

Every finding cites a concrete `path:line` for each member — two for a pair, one per member
for a larger group. It never makes a claim about a category or a layer. A correctly measured
single case placed under a category heading claims a reach it has not earned.

## 5. Two entry points, one method

**Audit mode** — the skill, whole project, all five stages. The left-hand comparison set
is every unit.

**Diff mode** — the agent, inside a review flow. Asymmetric: the left-hand set is only
the units the change adds, so no index is needed. Purpose sentences for the new units
become search terms against the codebase (concept words, involved types, callers),
followed by the same adversarial check. It answers: does what this change adds already
exist here?

The two differ in the left-hand comparison set, not in method. Building two agents for
them would plant a semantic twin inside the twin detector.

```
│   └── fixtures/twin-corpus/                  one planted case per taxonomy outcome

```

The agent is written to the shape of the `pr-review-toolkit` agents: frontmatter
(`name`, `description` carrying `When to invoke` scenarios, `model: inherit`, `color`),
persona opening, `## When to invoke`, `## Core Principles`, a numbered process,
`## Output Format` with a template, `## Common Anti-patterns to Flag`, `## Your Tone`.
The name deliberately echoes `silent-failure-hunter`.

## 7. Deployment

| Target | Form | Effect on `~/.claude` |
| --- | --- | --- |
| `~/.claude/skills/semantic-twins` | symlink into the repo | none — `/skills/*` already ignores the path |
| `~/.claude/agents/semantic-twin-hunter.md` | symlink into the repo | `/agents/` is tracked, so one ignore line is needed, otherwise `~/.claude` commits a machine-specific symlink |

One `.gitignore` line in the config repo, no `docs/` tree there, no growing exception
list. Because this repo is the backup, nothing is lost by leaving the deployed copies
untracked.

**Verifying symlink discovery is the first implementation step.** Whether Claude Code
discovers skills and agents behind a symlink is not asserted here — discovery happens at
session start, so it has to be tested in a fresh session before the layout is relied
upon. If it fails, `install.sh` falls back to copying, the repo stays the source of
truth, and `install.sh --check` reports drift.

## 8. Cost and honest limits

- An audit over 300 files costs roughly 300 cheap calls, one large call, and around 40
  verification calls.
- **Stage 2 is the recall bottleneck.** A poor purpose sentence sinks a pair invisibly:
  it appears nowhere as "checked and rejected". This cannot be designed away, only
  mitigated by the effect-not-construction rule. It is the design's honest weakness.
- No completeness claim. The report states what it examined and what it excluded.
- The tool does not satisfy the hook-enforced PR review gate, which recognises
  `pr-review-toolkit:*` agents and the `ck-docs-review` lanes. It is additive to that
  gate, not a substitute for it.

## 9. Testing

The deliverable is mostly prompts, which are not unit-testable. What is testable:

- `inventory.py` — exclusion rules, chunking boundaries, the generated-code heuristic.
  Ordinary TDD.
- The pipeline end to end, against a fixture repository carrying planted twins of each
  taxonomy class: a divergent pair, a stable pair, a justified cross-context pair, a
  generated-code decoy, and a near-miss that must be refuted. A run that fails to report
  the divergent pair, or that reports the justified pair as a finding, is a regression.
  This fixture is the only meaningful acceptance test for the prompt stages.
